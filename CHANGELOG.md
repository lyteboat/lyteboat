# Changelog

lyteboat has no releases. The tracked dsh release is in `dsh.upstream.json`.

## Unreleased

lyteboat is an agent harness for business agents, built as Cordis plugins on DeepSeek Harness (dsh) 0.1.7-rc.2, and a distribution of dsh: it owns the source of dsh's kernel packages under their published names and promises plugins written against dsh the protocol, interfaces, and behavior of that release (`dsh-compat/COMPAT.md`).

### Kernel

- 14 dsh packages under `dsh/` (`dsh/kernel.json`: `dsh-llm`, `dsh-session`, `dsh-system-prompt`, `dsh-tools`, `dsh-skill`, `dsh-agent`, `dsh-agent-loop`, `dsh-session-projection`, `dsh-session-persistence`, `dsh-session-persistence-jsonl`, `dsh-compaction`, `dsh-compaction-basic`, `dsh-agent-loop-testkit`, `dsh-api-session-controller`), imported from dsh-v0.1.7-rc.2 and resolved by name for the whole dependency graph; their bundles build byte for byte as npm publishes them. Every other dsh package is installed from npm at the tracked version.
- Four registered extensions (`dsh-compat/contract/extensions.yml`), listed at runtime by the `lyteboatDistro` service:
  - `agent-loop-intake`: the `lyteboat/intake` waterfall, after the inbox claim and before prompt assembly; a `reply` answers the claimed messages with an assistant message (source provider `lyteboat`) and no model request.
  - `agent-loop-pre-assemble`: the `lyteboat/pre-assemble` waterfall, before the system prompt is assembled, so skill routing and tool activation shape the same step's request.
  - `session-append-ignorable`: `Session.append(type, data, { ignorable: true })` marks an informational record of a type dsh does not know, so dsh's persistence and the official release read a log past it.
  - `session-controller-prompt-source`: `SessionPromptRequest.sourceFields` adds a caller's fields to the source of the user message a session-controller `prompt` appends, beside `kind`, `rpcId`, and `clientTimeZone`, which it refuses to overwrite.
- The kernel behaves as the official release does, including its request series: a tool-set change between requests appends a `developer/message` from the `tool-registry` source, and on a route that declares `toolUpdate` (dsh's default `deepseek-flash` is `addition-only`) the change continues the series instead of starting a new one.

### Plugins

Every plugin and bundle module default-exports one class (a `Service` subclass when it publishes a service) with `static inject` and, when it takes configuration, `static Config`; none exports `name`, `inject`, a `Config` value, or `apply` beside it.

- `@lyteboat/distro`: the `lyteboatDistro` marker service, naming the dsh release the kernel comes from and the extensions this build carries. A plugin that uses an extension injects it, so it stays unloaded on the official release.
- `@lyteboat/agent-def`: a business agent's one declaration. An agent module default-exports `lyteboatAgentDef({ agentId, agentName, … })`: `persona` (dsh-persona's config), `skillDirs` (default `assets/skills` when it exists; `[]` mounts none), `skillRouting`, `toolPolicy`, `modelRequest` (temperature, max tokens, and stop sequences laid over every loop request), `tools(host)` (the agent's own tools with their lyteboat metadata), `admission(host)`, `a2uiRenderTool`, and `eventListeners(host)` (listeners on any event dsh delivers per agent). It returns the plugin class that is the agent directory's row; mounted in the agent's standing scope, the row checks the declaration strictly (an unknown key fails, named with its path; each shape is tied to its owner's type at compile time) and that `agentId` names its directory, then hands each field to the host service that owns it, as effects withdrawn when the agent unloads. What the hooks return is checked too: a tool entry with an unknown key, or a listener on an event dsh does not deliver per agent, fails the mount. The hooks receive `LyteboatAgentHost`, one per mounted agent: `agentPath()`, and bound `a2ui.renderCard`, `auxLlm.generate`, `requestContext.contextOf`, and `toolPolicy.activate`. The agent rows `@lyteboat/tool-policy/agent`, `@lyteboat/skill-router/agent`, and `@lyteboat/a2ui/agent` are gone: their settings are the def's `toolPolicy`, `skillRouting`, and `a2uiRenderTool`; lyteboat has no releases, so there is no migration.
- `@lyteboat/tool-policy`: tool visibility (`always` / `auto`, with activation by a skill or in `lyteboat/pre-assemble`) and tool-result state deltas folded into the `lyteboatState` projection, enforced at two seams (visibility, state). An agent's `toolPolicy` (in its `lyteboatAgentDef`) declares policy for tools other rows register, and `inherited: visible | hidden` (absent: `visible`) for the inherited tools no declaration on the agent's chain names; `hidden` hides them for good, and a tool the host registers through `ctx.toolPolicy.register` counts as declared. An unknown key of the policy or of a tool's policy fails at load. lyteboat has no confirmation step: sandbox and human approval are not part of it. `metaOf(name, scope?)` and `visible(scope)` take a scope key (an agent is its own): `visible` now answers the tools a new agent under a standing scope sees before anything is activated (its `auto` tools and, with inherited tools hidden, the undeclared inherited ones left out); a running agent's current view is `ctx.tools.schemas(agent)`.
- `@lyteboat/aux-llm`: side model calls (a router's, an intake classifier's), each under its own deadline and recorded as an ignorable `lyteboat/aux-llm-call` (route, system, prompt, answer or failure, duration); an answer cut off at `maxTokens` is a failure. `reasoningEffort` sets the effort every side call requests.
- `@lyteboat/request-context`: the request a human message answers to (request id, owner, the agent it went to, trace id, context, admission verdict) rides the message's own source (`source.lyteboatRequest`); the `lyteboatRequest` projection (state version 3) keeps the session's context until a request brings another, and the session's owner, its first request's. The owner is typed, `{ kind: 'user' | 'operator' | 'system', id }`: `/chat` records `user:<user_id>`, the web pages `operator:web`, `lyteboat try` `operator:cli`, an eval run `system:eval` (not to be confused with dsh's `source.kind: 'user'`, which every human message carries). Tools read the request; the model never sees it. A session log recorded by an earlier build carries a string owner and no longer folds; lyteboat has no releases, so there is no migration: remove such sessions under `$LYTEBOAT_HOME/sessions`.
- `@lyteboat/intake-guard`: admission ahead of the loop. An agent registers an admission function; a caller submits each request through `intakeGuard.submit(agent, { text, context?, requestId?, owner?, agent? }, signal)`, which admits it and follows it up with the verdict recorded on the request. A reply verdict (text and cards) answers the turn without a model request; a message that arrives unadmitted is admitted in the loop.
- `@lyteboat/skill-router`: skill load modes over the dsh skill registry. `full` puts every skill body in the system prompt; `dynamic` routes each user input through a side call (the reference router prompt, sticky on null, errors, and timeouts; `historyWindow`, `timeoutMs`, and `maxTokens` (default 200) configurable, with an optional route of its own), activates the chosen skill's `requiredTools`, and enters its body as dsh's own skill-invocation message, so a routed session reopens and continues. An agent's `skillRouting` (in its `lyteboatAgentDef`) sets the mode per agent. `settingsFor(scope)` answers the settings of an agent or a preset's standing scope.
- `@lyteboat/a2ui`: the reference A2UI template engine (manifest resolution, transforms DSL, walker, contract validation against a domain-neutral default component catalog), the `render_a2ui` tool (an agent's `a2uiRenderTool`, through `registerRenderTool`), `renderCard`, `cardsPresentationMeta`, and `cardMarker` for an agent's own tools, the `lyteboatCards` projection, `turnParts`, which lays out a finished turn: cards by emission mode (`immediate`, `deferred`, `deferred_discard`) and the answer's `[[card:<area>]]` markers, and `liveTurn()`, which lays a turn out as it happens (the answer's deltas and the session's events) into the parts `turnParts` gives for the same log. A card with an unknown `emission_mode`, a malformed manifest, or a `compute.js` that exports only its default fails at load.
- `@lyteboat/agent-catalog`: scans agent roots (a subdirectory with `agent.cordis.yml`, `agent.yml`, `lib/agent.js`, or `src/agent.ts` is an agent, its kebab-case name the id; its rows are `agent.cordis.yml` when there is one, otherwise the one row `./lib/agent.js`, whose default export must be a `lyteboatAgentDef` naming the directory; the agent's definition, that row or the one module `agent.cordis.yml` names by a relative path whose default export is one, gives the display name, `agentName`, and two such rows fail), declares each to dsh's preset registry with the directory as base URL once the host tree has settled, and reports the agents that fail to read or mount; each entry names the agent's working directory, `<workdirsDir>/<id>` (`workdirsDir` defaults to `$LYTEBOAT_HOME/agent-workdirs`), which the catalog does not create; `whenReady()` rejects in strict mode (the default), `list()`, `get(id)`, `failures()` report. Two roots holding one id, or an included id no root holds, fail. `reload()` withdraws every declaration and declares the agents the roots hold now (a running session keeps the agent it started with); with `watch`, a change under a root reloads after `watchDelayMs`.
  - The agent manifest: an agent directory's optional `agent.yml` (`LyteboatAgentManifest`: `name` (which must equal the def's `agentName` when both are given), `description`, `order`, `version` as `1.2.3` or `1.2.3-rc.1`, `model` as `{ provider, model, reasoningEffort? }`) replaces `preset.yml` and is read strictly: an unknown key or a malformed version fails the agent. A directory that still holds `preset.yml` fails with a message to rename it; lyteboat has no releases, so there is no migration.
  - The agent's identity: the catalog computes each agent directory's digest (every regular file except, at the top level, `tests/`, `evals/`, and `agent.release.json`, and, at any depth, `node_modules/`, dot entries, and `*.tsbuildinfo`; POSIX paths sorted by their UTF-8 bytes; sha256 over `path NUL sha256(content) LF`; a symbolic link fails the agent), and each entry carries `identity` (`{ id, version?, digest }`) and the per-file hashes.
  - `enforceDeclaredModel`: an agent whose `agent.yml` declares a model other than the process's default model (provider, model, and reasoning effort compared exactly) fails before its code runs. Breaking: `lyteboat serve` and `lyteboat eval` set it, so they refuse such an agent; `lyteboat try` and `lyteboat web` do not.
  - `pinnedAgents`: an agent a release lock pins must have the lock's version and files; one that differs fails before its code runs, naming each changed, added, and removed file, and a pin for an agent the roots do not declare fails `whenReady()`. The order in which an agent is declared: its manifest and digest are read, then the pin and the model are checked, then it is registered.
- `@lyteboat/chat-api`: `/chat` on the host web server, beside `GET /agents` and `GET /health`. A message enters its session through dsh's session controller (a new session under the requested agent, in the agent's working directory, or a continued one checked against its owner and agent) with its request (request id, owner `user:<user_id>`, the agent's identity, trace id, context) on the human message; `GET /agents` lists each agent's `version` when its manifest declares one. The answer is one JSON body (`outcome`, `response`, `cards`, `tool_calls`) or the enterprise event stream: AGUI envelopes numbered from 1, at most one reasoning pair (reasoning deltas, tool calls), at most one text-message pair (text deltas, each card where the answer marks it), and exactly one `run_finished` (with `run_outcome`) or `run_error`, with a keep-alive comment while idle. `auth: shared-secret` checks a bearer token resolved from a credential reference per request; `auth: none` serves a loopback listener only; an unknown config key fails the row, and with it the service's startup (exit 1). A session the caller does not own (another user's, one an operator or an eval run started, or one with no owner) answers as one that does not exist (404), a repeated `message_id` in a session is refused (409), a session's messages queue, and a stream whose caller leaves cancels its running turn while the messages queued behind it still run. `registerFrameDecorator` lets an agent row add fields to its frames; changing a field the protocol owns fails the frame.
- `@lyteboat/eval-runner`: an agent's eval cases (YAML files, the agent directory's `evals/` by default, read strictly: an unknown key, a blank message, a non-kebab-case or repeated id, or a regular expression that does not compile fails the load). Every case is a new session in the agent's working directory whose turns go through dsh's session controller with their request (owner `system:eval`) on the source; after each turn the session is read for the active skill, the tools called, the cards shown (in any order), the outcome, the answer text, and the loop's model calls, and each expectation is a check with its expected and actual values. A real run records every case's session (the physical header dsh's persistence writes, then the events); a replay answers every model call from those recordings through an `llm/stream` listener, with no provider and no key: sessions are bound to their case's recording by id, loop calls come from the script dsh's replay derives from the recorded assistant messages, and side calls from the `lyteboat/aux-llm-call` records. Every turn's request carries the agent's identity. The run is written as `run.json` (`LyteboatEvalRunRecord`: the agent's identity, the model the recorded loop requests used, taken from their request headers, the mode, and the totals; a replay records no model, and a run whose requests used more than one model fails), `results.jsonl` (no timings, so one recording replays into the same lines), `sessions/`, and `report.md`; `compare` lists the checks whose results differ between two runs. Its second entry, `@lyteboat/eval-runner/records` (`ctx.evalRecords`), reads for the Studio without a session controller: the run directories under `$LYTEBOAT_HOME/evals` (each `run.json` through the contract's schema, cached by its size and time; one it refuses is listed without it and warned), one run with its results, the checks that differ between two runs, an agent's case files one by one (a file that does not load, or repeats an earlier file's id, says why), and removing a run. `EvalRunOptions.caseIds` runs only those cases.
  - The release gate, `evalRunner.release()`: an agent is released when its `agent.yml` declares a version and a model (step `manifest`); `evals/baseline` is a real run (`baseline`) whose `run.json` and every recorded human message name the agent's current identity (`stamps`) and whose every loop request used the declared model (`model`); a replay of the baseline through this build shows every turn as recorded and passes (`replay`); and no lock already releases the same version with other content (`version`). It then writes the lock `<agent>/agent.release.json` (`LyteboatAgentRelease`: the agent's id, version, and digest, the model, `dshBase` (the dsh release of this build's kernel), the per-file hashes, and the baseline's start, case, turn, and check totals, and the sha256 of its `results.jsonl`), with its keys in a fixed order, so releasing the same agent again writes the same bytes. What the lock does not cover: lyteboat's own plugins and bundles (serve with the build that released), the launcher's overlays (the profile patch, `--patch`, `--plugin`), the side calls' routes (they follow the host's default model), the model a resumed session keeps from its earlier request header, dsh's `/api` on the service, the request contents (a replay proves the same model answers show the same skill, tools, cards, outcome, and text through today's code), and what the digest leaves out (dot entries at any depth, files and directories alike, the environment, the agent's `node_modules`, and code outside the agent directory: a row naming a relative path out of it, or a relative import that leaves it).
- `@lyteboat/web-pages`: lyteboat's pages in dsh web. Its browser face (`./client`, declared by `dsh.client`) adds the Agents page (the catalog's agents with their display fields, the ones that failed and why, a reload) and the Evals page (the runs under `$LYTEBOAT_HOME/evals`, newest first, and one run's report; a `run.json` the contract's schema refuses, such as a run recorded before the agent identity, is left out with a warning) as main panels with sidebar entries, and a lyteboat tab to a session's right sidebar: it sends the next message with a request context (a JSON object) and shows the session's active skill, request (context, owner, admission), cards (as JSON), and state through dsh's projection hooks, live as the turn goes on. Its Host face answers the pages at `/api/lyteboat/<endpoint>` on dsh's connection (exact routes behind dsh web's trust fence and login, in dsh's RPC envelopes, so the pages call it through dsh's own browser transport): `agents`, `agents/reload`, `session/send` (a message queued through the session controller with its request context and the owner `operator:<owner>`, the row's `owner` config, `web` by default, as `/chat` sends one; without the agent's identity, since `lyteboat web` reloads agents while a session keeps the code it mounted), `evals`, `evals/report`. A refusal is `invalid_request` or `not_found`. `pnpm run build` bundles the browser face (`scripts/dist/bundle-clients.ts`) into `lib/client.js`, the loader factory dsh web runs, as dsh bundles its own.
- `@lyteboat/studio-auth`: the Studio workshop's sign-in (`ctx.studioAuth`). Internal mode: accounts an operator makes with `lyteboat studio account` (`$LYTEBOAT_HOME/studio/accounts.json`, scrypt N=16384 with a salt per account, never a plain password), a signed bearer token (HMAC-SHA256, 12 hours by default), one answer for an unknown username and a wrong password, and five failures of one username from one address locking it for 30 seconds. Gateway mode: an authorizing gateway's shared secret (a credential reference, compared in constant time) and user-id header on every request, 401 without them, and an identity seen for the first time granted viewer. Role grants admin, editor, and viewer (`grants.json`): through Studio nobody changes their own, and the last admin stays an admin.
- `@lyteboat/agent-inspector`: what an agent is made of (`ctx.agentInspector`), read from its standing scope under a lease (`agentPresets.acquireScope`) without creating an agent instance or writing to disk: `tools(id)` (each tool's schema, its declaration (`always`, `auto`, or `inherited`), how it reaches the model (`always`, `activated`, `hidden`), and the skills that require it), `skills(id)` (sorted by name, with required tools, a metadata problem instead of dropping the skill, and the SKILL.md path; and the routing mode, provider, and model), and `skill(id, name)` (with the body the model loads); an agent the catalog does not serve answers undefined.
- `@lyteboat/session-index`: an agent's stored sessions (`ctx.sessionIndex`), read through `sessionPersistence` with read handles, which never take a session's write ownership, so it runs beside the serve process that writes them. `list(agentId, query)` answers the sessions of the agent's working directory newest first, a page at a time, within a time window on their last update and optionally of one owner; eval runs (owner kind `system`) and sessions whose requests name another agent are left out. `find(agentId, text, query)` looks, case-insensitively, at the session id, the human messages, and the requests' trace ids of the 500 newest sessions of the window. `detail` folds one session into its timeline, in log order: human messages with their request (a turn's side calls follow its message), skill invocations, model answers with their timing from the step's start, tokens, and whether the admission answered, tool calls paired with their results (the areas of the cards they rendered, their state deltas, a mark when a later surface replacement pruned them), side model calls, compaction entries, and turn ends with their outcome; imported history is marked and left out of the summary's counts (errors: failed tool results and turns; rejected; aborted; slow: model answers and tool calls of 10 seconds or more). `raw` answers the stored header and events. A session's fold is cached by its storage revision, and an agent's listing is reused for two seconds.
- `@lyteboat/run-metrics`: run metrics of a service's turns, for the Studio's Dashboard. The recorder (`@lyteboat/run-metrics`, mounted by serve) appends one line per turn of a session a preset composed (`LyteboatRunMetric`: agent, session, turn, owner, start, duration, time to first content, steps, model requests, side calls, the tools called with their durations and errors (dsh's `skill` load left out), the skills activated and the active one, outcome, error code) to `$LYTEBOAT_HOME/run-metrics/<YYYY-MM-DD>.jsonl`, the UTC day of the turn's start, after the turn ends, and keeps a heartbeat file per process (`running/<host>-<pid>.json`, the turns it runs now) rewritten at each turn's start and end and every `heartbeatMs` (10 s), removed when the recorder stops. Its listener only folds in memory; the files are written in order through an asynchronous queue, and a write that fails is logged and never reaches the turn. Nothing enters a model request or the session log. Day files older than `retentionDays` (90) are removed when it starts. The reader (`@lyteboat/run-metrics/reader`, `ctx.runMetricsReader`, mounted by the Studio) answers the turns that started in a range, of one agent or all, caching each day file until its size or modification time changes and skipping a line that is not a metric with a warning, and the running turns of heartbeats written in the last 30 seconds.

Starting, stopping, and deleting are audited (`eval.start`, `eval.stop`, `eval.delete`). The Dashboard's activity feed lists eval runs. The Dashboard, read through `runMetricsReader`, `agentInspector`, and `sessionIndex`, for any role, ported from the original Studio's dashboard and checked against golden fixtures its own functions generated: `dashboard/health?from&to[&agent][&bucket][&compareFrom&compareTo]` (the performance view of one agent or every agent the catalog serves: completion rate, technical failures, incomplete runs, controlled exits (aborted, and the turns the admission answered), contention, first-content and duration percentiles (nearest rank), steps, tool calls and errors, skill triggers, active users, and the peak of users with a turn running (a sweep over each turn's span), bucketed by 30 minutes up to 12 hours, 60 up to 48, a day beyond, or as asked (a window of more than 500 buckets is refused), with the top six tools and skills and an optional comparison window; answers reused for 30 seconds), `dashboard/summary` (the static view: totals, six-month cumulative trends, skills per agent and the tools skills require, the sessions' coverage and message bands, the twelve newest activities; reused for 2 seconds), and `dashboard/running` (the turns serve processes run now, per agent). Failed logins, grant changes, reloads, and hot-fixes are appended to `$LYTEBOAT_HOME/studio/audit.jsonl`.
- `@lyteboat/history-import`: external conversation history (entries grouped into rounds by trace id, half rounds dropped, ordered by create time) turned into a session seed of closed turns.
- `@lyteboat/contracts`: lyteboat's declarations over the dsh seams: tool and skill metadata (`LyteboatToolMeta` with `visibility` and `stateDelta`; `LyteboatInheritedToolVisibility`; `LyteboatSkillMeta` with `requiredTools` only), the request envelope and its typed owner (`LyteboatRequest`, `LyteboatRequestOwner`), the agent manifest, model, and identity (`LyteboatAgentManifest`, `LyteboatAgentModel`, `LyteboatAgentIdentity`; `LyteboatRequest.agent`), an eval run's `run.json` (`LyteboatEvalRunRecord`), the release lock (`LyteboatAgentRelease`), the kernel's `lyteboat/*` events (re-exported), the `lyteboat/aux-llm-call` record, the projection keys, the prompt orders `LYTEBOAT_STATE_CONTEXT_ORDER` (130) and `LYTEBOAT_SKILLS_SECTION_ORDER` (450), `LyteboatDistro`, and the zod schemas of the JSON envelopes it declares. `LyteboatTurnOutcome` names how a turn ended for a caller that submitted a request: `completed`, `tool_stopped`, `rejected` (the admission answered in the loop), `stopped_by_limit`, `aborted`, or `errored`; `LYTEBOAT_TURN_OUTCOME_OF_REASON` maps a `turn/end` reason to it (a reason not listed is `errored`), for the eval runner, the session index, and the run-metrics recorder alike. `LyteboatRunMetric` and `LyteboatRunHeartbeat` are the run-metrics files' lines, with their schemas. `LYTEBOAT_EVAL_RUN_ID_PATTERN` is the shape of an eval run's id. The projections that fold a lyteboat envelope (`lyteboatState`, `lyteboatCards`, `lyteboatRequest`) throw on a malformed one.

### Bundles and the launcher

- `@lyteboat/host`: the host bundle every profile lists, with lyteboat's service rows over dsh-base; it turns off dsh-base's `session-log-deepseek` and `session-telemetry-otel` rows, so the model provider receives the request only and no session leaves the machine.
- `@lyteboat/business-base`: the base of the business modes (a patch and nothing else), listed by the `try`, `serve`, and `eval` profiles after `@lyteboat/host` and before the mode bundle; a business agent gets only what its own composition declares. It turns off dsh-base's coding tools and the services only they use (bash, pwsh, jobs, the file tools, todo, goal, plan mode, subagents, PTC and workflow, the web tool, MCP resources); the sandbox rows, shell environment, subprocess, approval, and permission (so no sandbox or approval policy text reaches the model, and a session starts without permission events; `fs` comes from `dsh-fs-local`); spilling (a large tool result is pruned, not spilled to a file); the working directory's AGENTS.md, the installed-package inventory, the plugin manager, the config editor, settings, and the session-title side call. The skill filesystem reads no default roots, and the system prompt gets no host persona and no harness identity. What a business agent's model request carries: its persona as the whole system prompt, the tools its composition declares plus dsh-base's `skill`, and none of the host's policy text, instructions, or package list. dsh's web services stay on the host, out of the model's sight: an agent that wants web search lists `@deepseek-ai/dsh-tool-web` in its own composition, as it lists any dsh tool it uses. A `--plugin` file or a community plugin that injects a service the base turned off (shell, subprocess, approval, sandbox policy) stays pending in a business mode; `--patch` can turn a row back on for a local experiment. Known model-visible leftovers: dsh's skill-invocation message names the skill's absolute directory, compaction's summarizer instructions describe a coding assistant, and a persona's `{{cwd}}` renders the server's path.
- `@lyteboat/try`: the one-shot bundle behind `lyteboat try` (named `run`, then `headless`, before; `lyteboat headless` is now an unknown command, and dsh's own `dsh-headless` keeps its name): it composes the selected agent, which `@lyteboat/agent-catalog` declares from its `--agents` root, in the agent's working directory (created here if missing), resumes a stored session under the agent it ran with from any directory, or seeds a new session from imported history; then it submits the task with its request context, the owner `operator:cli`, and the agent's identity, drives it to quiescence, prints the answer with its cards placed (`[card <area>]` lines) to stdout and the session id to stderr, and exits. Without `--agent` it runs in the directory it was started in and the model has the `skill` tool only: it serves plugin smoke tests and quick checks, not coding. The operator at the command line can continue any session of an agent in the same home, a `/chat` user's included, once no running `lyteboat serve` holds it (the session keeps its first owner).
- `@lyteboat/serve`: the service bundle behind `lyteboat serve`: it declares every agent of its `--agents` roots through `@lyteboat/agent-catalog` (a session names its agent; none is the default), mounts dsh's session controller with its host services (workspace, connection, file upload) and no web UI, listens where `--host` and `--port` say, and serves `@lyteboat/chat-api` there; a session runs in its agent's working directory, wherever the service was started. It mounts the run-metrics recorder, whose files the Studio's Dashboard reads. With `--release <lock>` (repeatable, exclusive with `--agents`) it declares only the released agents, pinned to their locks: a lock's directory is its agent's directory (named by the agent's id), its `dshBase` must equal this build's `lyteboatDistro.dsh` (checked by the startup row before any row that reads the invocation starts), and an agent whose version or files differ from its lock fails. Its catalog enforces the declared model. It disables live reload; an agent that fails to mount stops the service, and otherwise it prints where `/chat` listens.
- `@lyteboat/web`: the bundle behind `lyteboat web`, over dsh-web-app: its startup row takes dsh web's flags and `--agents` and `--agent` (dsh web's own startup row, which refuses a flag it does not know, is off), the agent catalog declares every agent of the roots without stopping on one that fails and reloads them when a root changes, the web pages join dsh web's, and dsh's coding presets are off; a new session runs `--agent`, else the first agent of the roots. The agent plane dsh web moves behind its presets (the skill tool and catalog, compaction, the file, shell, and subagent tools) is back on the host as dsh-base has it; the workspace's AGENTS.md and the package inventory stay out of model requests. `lyteboat web` does not list the business base: it keeps dsh web's own capabilities, sandbox and approval included, so its sessions do not run the way `/chat` runs them; `lyteboat eval` and `lyteboat try --agent` run an agent exactly as `/chat` does.
- `@lyteboat/eval`: the bundle behind `lyteboat eval`: it declares the one agent the cases talk to, mounts dsh's session controller with its host services and no web UI, runs `@lyteboat/eval-runner`, prints each case as it finishes and where the report is, and exits 0 when every check passed, 1 when one failed (or a comparison found a regression, or the release gate refused), 2 when the run could not start. The catalog enforces the declared model. `release` puts the agent through the release gate: stdout names the lock on success (`lyteboat release: <id> <version> (<digest>) released; lock: <file>; replay: <run>/report.md`), stderr the step on refusal (`lyteboat release: refused at <step>: <reason>`). Live reload is off; the business base keeps the session-title side call off, which a replay has no recording of. `--case <id>` (repeatable) runs only those cases (an id no case file holds fails the run); `--run-id <id>` names the run's directory under `$LYTEBOAT_HOME/evals` (one path segment; one that exists is a usage error), which is how the Studio starts a run it can follow. Eval sessions share their agent's working directory with its `/chat` sessions and are told apart by their owner.
- `@lyteboat/studio`: the bundle behind `lyteboat studio`, over the business base so an agent's tools and skills mount as serve mounts them: the agent catalog (not strict, reloaded when a root changes), the agent inspector, the session index, the run-metrics reader, the eval records, the host web server, studio-auth, studio-api, and studio-web; no session controller and no client connection, so Studio serves neither `/chat` nor dsh's session channel; the session projection cache is off, so reading a session never writes it. In account mode a Studio without accounts refuses to start and names the command that makes one.
- `@lyteboat/cli`, the `lyteboat` launcher (adapted from dsh's CLI): profile templates `try` (dsh-base, host, business-base, try), `serve` (dsh-base, host, business-base, serve), `eval` (dsh-base, host, business-base, eval), `studio` (dsh-base, host, business-base, studio), and `web` (dsh-base, host, dsh-web-app, web) under `$LYTEBOAT_HOME` (default `~/.lyteboat`, exported as `DSH_HOME`, and its `.agents` as `DSH_AGENTS_HOME`, before any dsh package loads); a profile whose template bundle is skipped fails the boot. A profile directory whose bundle list is not its template's fails at boot (`profile "<name>" at <dir> lists bundles [...], but this lyteboat's "<name>" template is [...]`), and so does a serve or eval profile an earlier build created without the business base (an existing `profiles/headless` is no longer read): set `dsh.profile.bundles` in the directory's `package.json` to the template's list, or move the directory away to have it recreated, keeping its `cordis.patch.yml`. A mode whose runner row (`lyteboat-try`, `lyteboat-serve`, `lyteboat-eval`) does not activate because a row it waits on failed fails the startup (`lyteboat: startup failed: <row> did not activate`, exit 1) instead of leaving the process up with nothing to do; dsh's own startup audit knows only dsh's runners.
  - `lyteboat try [options] "task"`: `--agents <dir>` (repeatable), `--agent <id>`, `--history <file>`, `--session-id <id>`, `--context <json|file>`.
  - `lyteboat serve [options]`: `--agents <dir>` (repeatable) or `--release <file>` (an agent's release lock, repeatable), one of them required, `--host 127.0.0.1|0.0.0.0`, `--port <port>`, `--auth none|shared-secret` (`none` on `127.0.0.1` only), `--secret-env <name>`.
  - `lyteboat eval [options]`: `--agents <dir>` (repeatable), `--agent <id>`, `--cases <path>` (repeatable), `--model real|replay`, `--from <run>` (a run's directory or its id under `$LYTEBOAT_HOME/evals`); `lyteboat eval compare <before> <after>`; `lyteboat eval release --agents <dir> --agent <id>`.
  - `lyteboat release [options]`: the eval profile with `lyteboat eval release`; exit 0 released, 1 refused, 2 a usage or startup error.
  - `lyteboat web [options]`: `--agents <dir>` (repeatable), `--agent <id>`, and dsh web's `--host` (loopback only), `--port`, `--no-open`, `--trusted-host`. `lyteboat studio` is reserved for the Studio workshop, and `lyteboat web` does not read an existing `$LYTEBOAT_HOME/profiles/studio` (to keep its patch, move its `cordis.patch.yml` to `profiles/web`).
  - `lyteboat studio [options]`: `--agents <dir>` (repeatable, at least one), `--host 127.0.0.1|0.0.0.0` (the latter with `--trusted-host`), `--port <port>` (8090 by default), `--trusted-host <name>` (repeatable), `--gateway-secret-env <name>` with `--admin <user-id>` (repeatable), `--anonymous-viewer` (account mode on 127.0.0.1 only), `--trace-link <url>` (with `{trace_id}`). `lyteboat studio account add <username> --role <role> [--display-name] [--user-id] | set-password <username> | remove <username> | list` reads a password from stdin, one line, and refuses a terminal.
  - `lyteboat config dump [options]`: the composed plugin tree (profile `try` by default); `--default` prints the bundle layers only.
  - All seven take `--profile <name>`, `--patch <path>` (repeatable), and `--plugin <file>` (repeatable).

### Example agent

- `@lyteboat/agent-finance` (`examples/agents/finance`): an agent kept deliberately minimal, built from public financial knowledge only. Three routed skills and three tools: an asset overview (one card), an allocation diagnosis by the 100-minus-age rule (two cards the answer places by markers), investor education on three concepts. The request context names the customer; its admission classifies each request with a side call before the loop (investor education and small talk pass, a request about the customer's money needs a known customer with an authorized account and otherwise gets a reply, the unauthorized card included, anything else gets the service scope; a failed classification lets the request through). It is one `lyteboatAgentDef` (`src/agent.ts`) with no `agent.cordis.yml`, and hides every inherited tool except `skill` (`inherited: hidden`). Its manifest declares version `1.0.0` and the model `deepseek-official/deepseek-flash`. Its eval cases (`evals/cases.yml`: an overview then a diagnosis, a diagnosis, education with and without a customer, a request out of scope, a customer with nothing authorized) and a baseline recorded against the real model with the agent's identity on every request (`evals/baseline/`), which its composition test replays without a model; `lyteboat release` passes on it without a key. The example commits no lock.

### Testing

- `@lyteboat/testing`: `createLyteboatUnitHost` (dsh's invariants, the dsh services, the kernel's agent loop, a scripted adapter), `MockAdapter`, `followUpAndWait`, and `mountAgentStandingScope` (an agent's row mounted as dsh's preset registry mounts it, with its instances in that scope; a row left waiting for a service fails it, naming the service) for unit tests; `/composition` (`bootComposition`, `startComposition`, `LYTEBOAT_TRY_BUNDLES`, `LYTEBOAT_SERVE_BUNDLES`, `LYTEBOAT_EVAL_BUNDLES`, `LYTEBOAT_WEB_BUNDLES`, `pluginFileRow`, `printedSessionId`) boots a composition in the test process, a one-shot run until it exits or a service while the test talks to it; `/chat-client` (`postChat`, `streamChat`) calls a `/chat` endpoint and reads its frames; `/scratch` (`createLyteboatScratch`) gives each run its own home and workspace; `/scripted-model` (`startScriptedModel`, `scriptedModelEnv`) is a DeepSeek Messages server that answers by purpose, can hold a reply, and records every request; `/session-log` reads and normalizes session logs; `/session-reopen` (`reopenRefusal`) runs a log through dsh's reopen check; `/process` spawns the built launcher.

### Compatibility gates

- G1: lyteboat's kernel build has the contract of dsh 0.1.7-rc.2 (`dsh-compat/contract/dsh-0.1.7-rc.2/`); every difference is a registered extension. Runs in `pnpm run test`.
- G2: upstream's own kernel tests pass unmodified on lyteboat's sources (`dsh-compat/tests/upstream-harness` lists the adaptations and exclusions). Runs in `pnpm run test`.
- G3, persistence, typert: upstream's cross-package tests, its durable-record schema, and its Typert generator, run against lyteboat's kernel in an upstream checkout (`pnpm run dist:overlay`).
- G4: the official release and lyteboat write the same session log for the same scripted run, including a tool set that changes mid-session on an addition-only route and on a route without tool updates.
- G5: 23 pinned community plugins install with `dsh plugin add`, run the same on both, and bind to lyteboat's kernel.
- G6: a session either side writes, the other reopens and continues.
- G4–G6 run with `pnpm run dsh-compat`; `pnpm run dist:delta -- --check` holds the classified-commit discipline for every change under `dsh/`; `pnpm run lint` runs oxlint, knip (declarations and dead exports), the layer check, the distro manifest check, and the sensitive-word check.
